## 1. 已实现的能力

- **上传**：`literature.services.upload_pdf`。先暂存并计算 SHA256，再检查真实 PDF 内容
  （格式 / 页数 / 加密 / 损坏），最后进入短事务完成幂等查找、Project 行锁、容量校验、
  文件归档与文献创建。体积上限在暂存流中即时生效，超大文件不会先落满磁盘。
- **去重**：同项目同 SHA256 返回既有 Paper，成功码仍为 201，带 `X-Resource-Reused: true`，
  不新增记录、不改其 `metadata` / `included`、不递增 `corpus_revision`。
- **幂等**：请求摘要包含**文件 SHA256** 与元数据。同键同体重放返回原响应（不重复落盘），
  同键异体返回 409 `IDEMPOTENCY_CONFLICT`。重放命中时本次暂存文件立即丢弃。
- **编辑**：`update_paper` 支持 `title` / `authors` / `year` / `included`，
  校验 `expected_version`，过期返回 409 `VERSION_CONFLICT` 并带回 `current_version`；
  实际内容变化才递增 `Paper.version` 与 `Project.corpus_revision`，内容相同不涨版本。
- **授权下载**：`Paper → Project → owner` 一次带 owner 过滤的查询完成归属校验，
  跨用户与不存在都表现为 404；响应只输出二进制与必要报文头，**不含任何磁盘路径**，
  非 ASCII 文件名按 RFC 5987 百分号编码。
- **arXiv 受理**：`import_arxiv` 校验 1—10 个互不相同的合法 ID（**不接受任意 URL**），
  初始化 `Job.result.items` 逐项 `pending`。幂等记录、Project 锁、空闲校验与提交后投递
  全部交给 `jobs.services.accept_job`，本模块不重复记录也不重复投递。
- **arXiv 执行**：`execute_import_arxiv(context, job_id)` 用 `context.job_id` 读取**当前**作业
  （重试产生的新 Job 有自己的账本，改旧 Job 会污染历史），逐项解析具体版本 →
  持久化 `resolved_source_id` → 下载 → 走与上传同一套 PDF 校验 → 登记。
  任一失败即整批 `failed` 但成功项保留；重试只补 `pending` / `failed`，沿用已冻结版本。
- **arXiv 客户端**：`fetch_metadata` / `download_pdf`，请求频率下限、超时、跳数上限、
  下载大小上限、非 PDF 内容拒绝；地址由服务端白名单构造，**每一跳重定向都重新校验主机**。
- **PDF 结构检查**：落在 `parsing.pdf`（与 `01` §4.3 的分工一致），
  `inspect_pdf_file(path)` 供上传阶段使用，`inspect_pdf(asset)` 供已登记资产使用。
  只认文件内容不认扩展名；损坏与加密 → 422 `UNSUPPORTED_PDF`，超页数 → 422
  `PAGE_LIMIT_EXCEEDED`，超体积 → 413 `FILE_TOO_LARGE`。

## 2. 关键设计决定

### 2.1 幂等查找在 PDF 校验之后

上传接口的幂等摘要必须含文件 SHA256，而 SHA256 只有读到内容才知道，因此顺序是
**暂存取哈希 → PDF 基础检查 → 事务内查幂等 → 去重与登记**。契约要求的
「幂等查找先于 PROJECT_BUSY」仍然成立：`PROJECT_BUSY` 判断在事务内的 Project 行锁
及幂等查找之后发生。重放仍会进行本次文件的基础检查，但不会重复归档或创建文献。

### 2.2 PDF 解析只在 parsing 模块

`literature` 不另建一套 PDF 读取实现。上传校验通过 `parsing.pdf.inspect_pdf_file` 完成，
M06 的文本提取与页面渲染继续留在同一文件，避免两处对「什么是合法 PDF」给出不同结论。

### 2.3 arXiv 响应按不可信输入解析

标准库 `xml.etree` 明确不防御实体扩展，且 `XMLParser` **不接受 `resolve_entities` 参数**
（早期实现用它做过防护，是无效的，已更正）。最终做法是：解析前直接拒绝任何含
`<!DOCTYPE` 的响应——真实 arXiv Atom 响应不含 DTD——从源头挡掉 XXE 与实体膨胀。
该行为由 `test_arxiv_client.py` 的 XXE 与 billion-laughs 用例守住。
因此 `pyproject.toml` 对 `apps/literature/arxiv.py` 单独忽略 `S314`，并在注释中说明理由；
这是**有测试背书的定点豁免**，不是无差别静音。

### 2.4 取消与进度写入的边界

`record_progress` 与普通账本写入只接受有效租约、`running` 且未被请求取消的任务。
若取消在发布前已经提交，导入不得登记文献；若取消在某次合法提交之后到达，已提交产物保留，
停止后续项并由协作取消流程收尾。账本校验和 UPDATE 处于同一短事务，Job 行锁持续到提交；
因此取消只能排在该次合法写入之前或之后，不能在校验成功与写入之间插入。

## 4.1 复核后的修正（2026-09-29）

独立复核在隔离环境中提出 9 类问题（10 项边界断言全部失败），已全部修复并回归。
完整对照表见[复核问题清单](M05_复核问题清单_2026-09-29.md)，要点：

1. **发布前在同一事务内复核执行资格**（P1）。下载在事务外进行，期间租约可能被恢复扫描
   替换、或用户已提交取消；此后写 Paper 会留下「任务失败但文献已入库」的不一致状态。
   新增 `_assert_publishable` 在写 Paper / 语料版本的同一短事务内锁定 Project 与当前 Job，
   校验 `lease_token`、状态与**取消时间**——取消时间必须从锁定的当前行读，
   不能用下载前的内存快照（这一条在修复过程中被测试抓出来过一次）。
2. **忙碌项目拒绝语料写入**（P1）。上传与编辑都补上 `require_project_idle`；
   顺序是「幂等重放 → 忙碌检查 → 其余校验」，因为契约把相同幂等键的重放列为忙碌例外。
3. **MIME 与流式上限**（P2）。存储与下载类型固定 `application/pdf`；
   下载改为 `client.stream()` 逐块累计，超限立即中断，并加整段下载的总耗时上限。
4. **幂等快照与连续重试**（P2）。幂等记录保存原受理响应快照；
   账本恢复沿 `retry_of` 链向上找最近一个真正有账本的尝试。
5. **受理账本与授权列表**（P2）。受理即写 `Job.result.items`；
   越权查询项目文献列表改为 404；重复上传立即清理本次暂存文件。

## 4.2 第二轮复核后的修正（2026-09-29）

第二轮复核确认第一轮修复有效（10 项原始用例全通过），但指出 5 项历史数据兼容与
导入边界问题。完整对照表见[第二轮复核](M05_第二轮复核_2026-09-29.md)，要点：

1. **下载类型不再读历史 MIME**。第一轮只固定了新上传的存储类型，下载接口仍在用
   `asset.media_type`，于是修复前遗留的 `text/html` 资产依旧按 HTML 返回。
   现在响应类型固定 `application/pdf`，历史库里存什么值都不影响出站类型——
   这比数据迁移更稳，也不依赖迁移是否被正确执行。
2. **账本写入纳入租约检查**。原先只比较 `lease_token`，而租约**过期**时 token 可能
   还没被恢复扫描替换，这个窗口期足以让旧 worker 在已判死的任务上写入新进度。
   `_lease_writable` 在短事务内同时校验 token、状态、`lease_expires_at` 与取消意图。
   此时尚未把调用方 UPDATE 纳入同一事务，第三轮发现的并发缺口已在第 4.3 节补齐。
3. **账本恢复优先级**。`_load_items` 原先一律从 `frozen_input` 出发，
   于是旧形态数据（中间尝试排队期间被取消、`result=None`）会用它的初始 pending 项
   截断更早的真实进度。现在优先用本次尝试已持久化的账本，回溯祖先时用
   `_has_progress` 过滤掉「等于没跑过」的账本。
4. **满容量与内容去重解耦**。去重规则是「同项目同内容」，与来源无关：
   同一份 PDF 可能早已以「上传」来源存在。满容量时先按来源版本查，再下载后按
   SHA256 查，只有真正需要新增才拒绝。
5. **总耗时上限覆盖全链路**。deadline 原先在最终响应头到达后才建立，重定向链
   每跳各耗接近单次超时的时长就能整体超限。改为在发出第一个请求前建立，
   每次出网前、每跳之后、每块正文之间都校验。

## 4.3 第三轮复核后的修正（2026-09-29）

第三轮复核提出两项遗留问题（完整报告见[第三轮复核](M05_第三轮复核_2026-09-29.md)）：

1. **账本资格校验与写入不在同一事务**。`_lease_writable` 在自己的事务里取得 Job 行锁、
   校验完就提交释放，随后的 UPDATE 只比对 job id 与 `lease_token`（取消不改 token），
   并发取消可以挤进两者之间先落地。现由 `_save_items` 用**外层事务**把校验与条件
   UPDATE 串起来，行锁持续到 UPDATE 提交；UPDATE 自身再带
   project / token / 租约有效期 / 状态 / 取消标记条件。
2. **总时限不能中断正在阻塞的等待**。原先每跳仍用初始 timeout，且只在阻塞结束后
   才检查截止时间，实际耗时可以超过总预算。现改为异步内核：
   `asyncio.timeout_at` 建立绝对截止时间，覆盖限流、全部跳转、连接、响应头与正文，
   到期由 asyncio 取消正在等待的 I/O；同步入口用 `asyncio.run` 桥接，不留后台线程。
   此时仍不能中断正在阻塞的网络等待，第三轮的可取消实现见第 4.3 节。

同时补了两条可判定的回归守卫（旧实现下会失败）：

- `test_ledger_write_holds_job_row_lock_across_check_and_update`：在 `_lease_writable`
  返回的瞬间用独立连接探测该行是否仍被锁住（`pg_stat_activity.wait_event_type = Lock`），
  直接判定「校验与 UPDATE 是否共享同一事务」。**已双向验证**：回退修复即失败。
- `test_slow_body_read_is_cancelled_at_total_deadline`：正文读取中阻塞时也必须在
  总预算内取消，而不是等 read timeout 走完。

另有一条 `test_retry_acceptance_waits_for_inflight_ledger_write`，
钉住「受理重试必须等到上一次尝试的账本提交」这一 `retry_job` 依赖的顺序。

## 4.4 第三轮修复的独立核对（2026-09-29）

> 第 4.3 节是修复方的实测记录；本节是**接手方的独立核对**，只记录核对结论、
   发现的测试可用性缺口与补入的守卫，不重复描述修复内容。

对第 4.3 节两项修复做了独立核对，**两项均确认正确落地**：

- `_save_items` 的外层事务确实把 `_lease_writable` 的 Job 行锁持有到条件 UPDATE 提交；
- `_stream_to_async` 的 `asyncio.timeout_at` 覆盖限流、全部跳转、连接、响应头与正文读取，
  各跳 timeout 取剩余预算，到期由 asyncio 取消正在等待的 I/O；
  同步入口 `_stream_to` 用 `asyncio.run` 桥接，未遗留后台下载线程；旧的 `_Deadline` 已删除。

核对中发现第三轮复核脚本的一处可用性缺口，已补强：

**第三轮「账本并发」复现用例无法捕获回归。**
`test_recheck_round3.py::test_cancel_committed_between_lease_check_and_ledger_write`
的断言被结构性关闭：`cancelled_before_write` 只在 `not connection.in_atomic_block`
时追加，而修复后校验与写入共用外层事务，该分支永不进入，末尾断言因此永不执行。
把修复回退成旧写法，这条用例**仍然通过**——它只能证明「取消没有死锁」，
不能证明「校验与写入在同一事务」。

因此新增可判定的守卫
（`tests/test_m05_review_regressions.py::test_ledger_write_holds_job_row_lock_across_check_and_update`）：
在 `_lease_writable` 返回的瞬间用独立 psycopg 连接探测 `jobs_job` 该行，
要求探测真的阻塞（`pg_stat_activity.wait_event_type = Lock`）。
**已双向验证**：回退修复时失败（"资格校验返回时 Job 行锁已被释放"），
修复到位时通过，连跑 4 次稳定。

同时补入两条守卫：

- `test_slow_body_read_is_cancelled_at_total_deadline`：正文读取中阻塞也必须在总预算内
