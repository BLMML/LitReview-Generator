## 1. P2：账本资格校验与写入仍不在同一事务

位置：`backend/apps/literature/services.py:621`—`625`，以及 `_lease_writable` 的事务范围。

修复前顺序：

1. `_lease_writable` 在自己的事务内锁定 Job，验证租约、状态和取消标记。
2. 该函数退出事务并释放锁。
3. `_save_items` 才执行 UPDATE，条件只有 Job ID 与 lease_token。

独立 PostgreSQL 双连接复现：在步骤 2 与 3 之间，另一个线程使用真实 `cancel_job` 提交取消。取消不改变 token，随后 `_save_items` 仍返回 True，账本被写入新的 `resolved_source_id`。这不是单纯静态推测；测试明确等待取消事务提交后，才允许原 worker 继续 UPDATE。

修复要求：把锁定当前 Job、资格校验、账本 UPDATE 放在**同一个**短事务内，锁不能在写入前释放；普通阶段与取消收尾明确区分。可配合带状态、取消标记及租约有效期条件的原子更新。只在更新前调用一个内部自行提交的校验函数，不能保证并发正确性。

已有「调用前就已过期 / 已终态」的测试不足以覆盖此窗口，需要保留并发取消在检查和写入之间到达的测试。

## 2. P2：下载只在阻塞结束后检查总时限

位置：`backend/apps/literature/arxiv.py:193`—`213`，`_stream_to` 中客户端及 `client.stream` 调用。

修复前在构造客户端时调用一次 `whole.remaining()`，每一跳的请求仍使用这个初始 timeout。`whole.ensure()` 能判断最终已经超时，却不能中断正在阻塞的响应头等待或正文读取。

确定性 HTTP 替身复现：总预算设为 1 秒，第一跳和第二跳分别模拟 0.75 秒响应头等待，替身遵守调用方传入的每跳 read timeout。记录到两跳 timeout 都是 `[1.0, 1.0]`。函数最终报超时，但直到 **1.937 秒**才返回，超过总预算。第二轮的受控时钟用例只检查「最终是否报错」，没有约束实际返回时间，所以仍能通过。

修复要求：将所有跳转、连接、响应头和正文读取包在同一个可取消的绝对截止时间中；每跳使用剩余 timeout 还不够，HTTPX 的超时按网络操作计算，持续缓慢出数据仍可能超出总时限。可参考项目模型网关已有做法，用 `AsyncClient` 配合外层 `asyncio.timeout()`，到期主动关闭响应、取消读取并清理暂存文件。

新增测试应同时断言错误类型、实际耗时和半成品清理，并覆盖慢响应头、重定向及正文读取中阻塞。

## 接手复核补记（2026-09-29）

上述两项修复经独立核对**确认已正确落地**，并发现两处需要补充的地方。

### 核对结论

- **账本竞态**：`_save_items` 确实把 `_lease_writable` 的 Job 行锁持有到条件 UPDATE 提交
  （`services.py` 中 `with transaction.atomic():` 包住校验与 UPDATE，UPDATE 另带
  project / token / 租约有效期 / 状态 / 取消标记条件）。修复成立。
- **总时限**：`_stream_to_async` 用 `asyncio.timeout_at(deadline)` 建立**绝对截止时间**，
  覆盖限流、全部跳转、连接、响应头与正文等待，各跳 timeout 取剩余预算；
  到期由 asyncio 取消正在等待的 I/O。修复成立。
- 同步入口 `_stream_to` 用 `asyncio.run` 桥接，未遗留后台下载线程；`_Deadline` 旧实现已删除。

### 补记 1：本轮「账本并发」复现用例**无法捕获回归**

`test_recheck_round3.py::test_cancel_committed_between_lease_check_and_ledger_write`
的断言被结构性地关掉了：其 `cancelled_before_write` 只在
`not connection.in_atomic_block` 时才追加，而修复后校验与写入共用外层事务，
该分支永不进入，末尾 `if cancelled_before_write:` 因此永不执行。
**把修复回退成旧写法，这条用例仍然通过**——它只能证明「取消没有死锁」，不能证明
「校验与写入在同一事务」。

已在项目内补一条真正可判定的守卫：
`tests/test_m05_review_regressions.py::test_ledger_write_holds_job_row_lock_across_check_and_update`。
它在 `_lease_writable` 返回的瞬间用独立 psycopg 连接探测 `jobs_job` 该行，
要求探测语句真的阻塞（`pg_stat_activity.wait_event_type = Lock`）。
已双向验证：**回退修复时该用例失败**（"资格校验返回时 Job 行锁已被释放"），
修复到位时通过，连跑 4 次稳定。
