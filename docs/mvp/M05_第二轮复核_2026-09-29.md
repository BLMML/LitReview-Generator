## 剩余问题（均为 P2）

### 1. 旧 PDF 资产仍可按 text/html 下载

位置：`backend/apps/literature/api.py:213`。

新上传时的 media_type 已固定，但下载接口仍直接使用 `asset.media_type`。模拟修复前遗留的 PDF 资产 `media_type=text/html` 后，下载响应仍为 `text/html`，并以 inline 输出。

修复：PDF 下载接口固定 `application/pdf`，必要时清理历史资产的错误 MIME。增加旧资产测试；只有新上传测试通过不能证明历史文件也安全。

### 2. 租约过期后仍可改写导入账本

位置：`backend/apps/literature/services.py:585`，特别是 `_save_items` 的更新条件。

该函数只匹配 Job ID 和 token，不校验状态、取消或 `lease_expires_at`。模拟元数据请求期间租约过期（恢复扫描尚未递增 token），返回后 `Job.result.items` 仍被写入新的 `resolved_source_id`。虽然发布 Paper 会被新检查阻止，但账本写入已经发生。

修复：把账本更新也纳入有效租约检查与短事务；普通阶段写入与取消收尾要明确区分，不能只比较 token。补测 token 未变但已过期，以及终态任务不可覆盖。

### 3. 升级前已取消的任务，重试仍可能丢失旧进度

位置：`backend/apps/literature/services.py:526`、`:558`、`:573`。

复现：J1 部分成功且失败项已冻结 v2 → 修复前创建的 J2 排队取消，`result=None` → 新版受理 J3。`retry_job` 正确把 J1 账本继承到 J3.result，但 `_load_items` 忽略当前 result，先命中 J2.frozen_input 的初始 pending 项，最终把成功项和冻结版本重置。

本次直接验证 J3.result 已正确继承后再调用 `_load_items`，实际得到两项 `pending`、`resolved_source_id=None`。现有回归测试虽然注释提到 null，但使用新版 retry_job 已自动填入账本，因此未覆盖旧数据状态。

修复：优先使用当前尝试的有效持久账本；回溯祖先时不能让中间尝试的初始 frozen_input 截断更早的真实进度。

### 4. 满容量时，已有相同 PDF 的 arXiv 导入被误拒绝

位置：`backend/apps/literature/services.py:767`。

复现：先手动上传 PDF 达到项目容量，再通过 arXiv 导入同一 PDF。前置容量判断只查 `source=arxiv/source_id`，由于已有文献来源是 upload，直接失败为 `PAPER_LIMIT_EXCEEDED`，不会执行后面的 SHA256 去重。

隔离测试将容量缩为 1：当前已有 1 篇，导入字节完全相同的 PDF，实际失败；预期 duplicate 且仍为 1 篇。这是相同规则的缩小样本，不要求新增文献超限。

修复：满容量时仍允许判定同哈希复用，只在真正需要新增 Paper 时拒绝；保留事务内最终容量检查。

### 5. 下载总时限没有覆盖响应头和重定向

位置：`backend/apps/literature/arxiv.py:195`、`:205`。

deadline 在最终响应头到达后才创建，此前请求 / 重定向耗时没有计入。HTTP 替身与受控时钟复现：总上限 60 秒，302 → 302 → 200 三次请求各耗时 40 秒，累计 120 秒仍成功。每次请求都低于单次 60 秒超时，因此单次 timeout 无法补足这个缺口。

修复：首次请求前建立整个下载的 deadline，各次连接、响应头等待、重定向和正文读取都受剩余时限约束；补测慢响应头、重定向链以及阻塞读取。
