## 2. 三个值得记录的判断

### 2.1 `_locked_job` 的 `locked=True` 不能解决所有问题

问题 2 与问题 3 看起来是同一处，但**要求相反**：

- 阶段发布要"校验**并**加锁"，且只允许**可写入**的租约通过；
- 终态收尾（取消）必须能处理**已被取消**的 Job——它本来就不处于可写入状态。

最初我把 `locked=True` 加进 `_locked_job` 并让收尾也调用它，结果正常的取消收尾
全部被 `check_execution_lease` 拒掉（自己的测试立刻报出来）。因此拆成两个入口：

- `_locked_job(ctx, run, locked=True)`：加锁 + 完整可写入校验，**发布用**；
- `_lock_job_row` + `_owned_job_row`：只加锁/只判"是不是当前尝试"，**收尾用**。

### 2.2 幂等指纹里不能有服务端产物

`create_run` 的请求指纹原先包含服务端生成的 `config_snapshot`。后果是**每次部署改配置，
浏览器对已受理请求的正常重放都会变成 409**——幂等键的作用恰好在这一刻最需要生效。
指纹只保留客户端请求身份（本接口正文必须是空对象），服务端配置在首次受理时冻结进 Run。

### 2.3 存在性检查必须走真实关系

`run_paper.analysis_id` 是"看起来很像存在"的字段名。反向 OneToOne 没有这个属性，
直接取会抛 `AttributeError`，而它恰好落在**最需要复用结果的重试路径**上——
首次分析全绿时完全看不到。修复后还额外要求 `status=ready` **且**产物确实存在：
半途中断留下的 ready 标记不可复用。

## 5. 仍未覆盖的部分

1. **真实模型输出未冒烟**：全部检查使用替身。真实 `assign_topics` / `compare_disputes`
   的归纳质量、条件对齐合理性与引用合规率要等 M14。
2. **主题归纳仍是单批调用**：`04` 第 3 节要求"分批主题归纳、合并与成员映射"。
   当前把全部单篇要素放进一次调用；语料接近 30 篇时可能触及模型上下文上限。
   这是**已知简化**，本轮未改变。
3. **争议比较的成员上限截断不告知用户**：超过 `max_papers_per_topic` 的成员被静默截断。
4. **`_save_topics` 与 `_save_disputes` 的替换策略会重建 ID**：同一 Run 内这些 ID 不稳定，
   因此下游若长期引用 `Topic.id` / `Dispute.id` 需注意。争议的**逻辑调用 ID** 已改为
   稳定位置种子，不受此影响。
5. **人工抽检**：主题划分与争议分类的学术合理性只能人工判断。
