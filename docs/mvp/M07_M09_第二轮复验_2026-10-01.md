## 1. [P1] 清理检查仍在事务外，入口状态写入也未受租约保护

位置：

- [analysis/services.py:714](<D:/LitReview Generator/backend/apps/analysis/services.py:714>)：`_release_processing_paper`。
- [analysis/services.py:735](<D:/LitReview Generator/backend/apps/analysis/services.py:735>)：`_mark_paper_failed`。
- [analysis/services.py:759](<D:/LitReview Generator/backend/apps/analysis/services.py:759>)：`_finish_cancelled`。
- [analysis/services.py:562](<D:/LitReview Generator/backend/apps/analysis/services.py:562>)：单篇入口改 processing。

### 已修复与残留的区别

原检查把旧 token 放在调用函数之前，新增的 `_attempt_is_current` 能正确拒绝，因此原有四项旧租约检查通过。现在的问题是这个查询在状态 UPDATE 的事务外完成，校验和写入之间仍没有 Job 行锁。

本轮用第二条真实 PostgreSQL 连接，在 `_attempt_is_current` 返回有效后、更改业务状态前，提交新的 lease_token，再让旧 worker 继续。确认新 token 已先提交后：

- release 把当前 processing 论文改成 pending；
- paper-failed 把它改成 failed；
- run-cancelled 把当前 processing Run 改成 cancelled。

另外，直接调用持旧 token 的 `_execute_run_paper`，当前数据库论文已经 ready。它先保存 processing，之后解析服务才抛 `INVALID_JOB_STATE`，最终 ready 论文仍被改成 processing。`execute_run` 第 338 行的 processing → pending 重置也没有持锁资格检查；此处是同类源码观察，本轮没有单独断言该重置路径。

影响：恢复扫描或后续尝试接管后，旧 worker 仍能改坏当前资源；现有短事务包住 UPDATE 并不足以消除检查与写入之间的窗口。

修复：所有状态修改，包括入口 processing、恢复重置、失败标记、取消收尾和交回 pending，都在短事务内锁对应 Job 并重新判定当前执行资格。取消使用允许 cancelling 的校验口径；不能用事务外 bool 作为写入授权。资源及 Job 终态按同一个被锁定的状态提交。

对应 4 个失败实例：

- `test_takeover_between_cleanup_check_and_write_cannot_be_overwritten` 的 3 个参数。
- `test_old_worker_cannot_mark_current_ready_paper_processing`。

## 2. [P2] 索引配置在正式调用链中仍丢失，召回查询也读取当前参数

位置：[analysis/services.py:534](<D:/LitReview Generator/backend/apps/analysis/services.py:534>)、[analysis/services.py:970](<D:/LitReview Generator/backend/apps/analysis/services.py:970>)、[retrieval/services.py:535](<D:/LitReview Generator/backend/apps/retrieval/services.py:535>)、[retrieval/index.py:354](<D:/LitReview Generator/backend/apps/retrieval/index.py:354>)。

直接把完整 config_snapshot 传给 `_stage_index` 时，原冻结配置测试通过。但正式 `execute_run` 先调用 `_frozen_config`，它仅返回 parsing / extraction / topics / disputes，**漏掉 index**。`_stage_index` 收到的配置没有 index，于是仍使用当前默认值。

完整流水线复现：创建 Run 时冻结 max_features=20000，执行前仅把当前默认值改成 1，实际 Run.ready 的 index_manifest 记录并使用 1。

检索链路也没有透传配置：`_resolve_index` 调用 `load_published` / `build_index` 时不传冻结 config。创建并成功发布 20000 的 Run 后，部署默认值改成 1；检索将旧产物判为不一致，重新构建 1 的索引，而不是使用该 Run 对应参数。

第三处是 `recall` 构造查询 n-gram 时读取 `index_config()`。同一份固定的 ngram_max=2 索引、同一问题 `attention accuracy`，仅修改当前默认 ngram_max=1，召回分数就从 1.023408 变成 0.927361。这是召回分数，不是重排 DTO 的 0–1 score；问题在于相同冻结索引和输入的输出发生漂移。

影响：快照与实际执行参数仍不一致；升级配置会让历史任务或检索改变输出。只修底层 `build_index(config=...)`，没有修调用者透传，不构成完整修复。

修复：`_frozen_config` 完整返回并校验 index；公开检索与内部检索选择明确的有效冻结索引配置并透传到 load / build；查询向量化使用该索引的参数，避免从当前 settings 再取 ngram_max。检索记录的索引配置应与实际采用的 Run 索引一致。

对应 3 个失败实例：

- `test_full_pipeline_preserves_frozen_index_config`。
- `test_retrieval_resolution_preserves_run_index_config`。
- `test_query_vector_uses_same_config_as_frozen_index`。

## 3. [P2] 主题数量校验仍受当前 settings 影响

位置：[analysis/services.py:1365](<D:/LitReview Generator/backend/apps/analysis/services.py:1365>)、[analysis/services.py:1072](<D:/LitReview Generator/backend/apps/analysis/services.py:1072>)。

主题提示词使用冻结的 max_topics，但 `validate_topics` 所用 `_RunScope.max_topics` 仍取当前 `settings.TOPICS_MAX`。实测：

- 冻结允许 2 个主题、当前设置降到 1：合法的 2 个主题被拒绝。
- 冻结只允许 1 个主题、当前设置升到 2：违反冻结上限的 2 个主题被保存。

影响：同一冻结 Run 在不同部署配置下，可能把合法输出判坏，或接受本应拒绝的输出。

修复：构造 scope 时传入对应阶段的冻结限制，让提示词、模型请求校验与领域校验使用同一份有效配置。第 1366 行 disputes.max_disputes 也仍读取当前设置，需一并处理；本轮直接复现的是主题数量的两个方向，争议数量这里只依据源码记录。

对应 2 个失败实例：`test_topics_schema_limit_is_frozen` 的 global-lower / global-higher。

## 4. [P2] COMMIT 失败时索引仍成为孤儿文件

位置：[analysis/services.py:1004](<D:/LitReview Generator/backend/apps/analysis/services.py:1004>)。

在 Run.index_asset 的 UPDATE 中失败，新增 committed_path 能清理文件，原测试因此通过。但它在 `with transaction.atomic()` 内就被置为 None，注释声称“已提交”，此时事务尚未退出。

本轮让事务退出时的 `connection.commit()` 抛 DatabaseError。Django 回滚后，确认索引 FileAsset 没有记录，磁盘索引 JSON 仍存在，因为异常处理已失去清理路径。

影响：提交阶段故障仍会积累无数据库登记的索引文件。

修复：提交成功后再解除清理责任；清理前确认最终文件未被已提交记录引用。应覆盖 UPDATE 失败和 COMMIT 失败两种路径，避免对提交结果不明确的文件直接删除。

对应失败实例：`test_index_commit_failure_removes_moved_file`。

## 5. [P2] 争议阶段只在开头清空，重试失败会删除原完整产物

位置：[analysis/services.py:1119](<D:/LitReview Generator/backend/apps/analysis/services.py:1119>)、[analysis/services.py:1211](<D:/LitReview Generator/backend/apps/analysis/services.py:1211>)。

当前策略先在独立事务中删除旧争议，随后调用各主题的模型并逐主题追加。因此成功重试确实不会把同一候选累加为两条，原测试通过；但这不是整个争议阶段的原子替换。

复现：首次争议阶段已提交 1 条完整候选，在阶段返回后注入可重试中断；正式 retry_job 创建新尝试，第二次比较超时。实际第二次 Run.failed，而原候选集合从 1 条变成 0 条。

这次检查没有使用上一轮的 analysis_id 兼容属性，重试关系修复已实际生效。模型超时由测试替身注入，没有付费调用。专项断言允许“正确复用完整阶段后直接 ready”；若仍尝试重建且失败，则必须保留原完整候选。

影响：已完整提交的成功产物不再保留，恢复过程中会删除已有分析结果。当前文档称 `_save_disputes` 原子替换，实际删除在前一个事务，创建在后续多个事务。

修复：优先复用可校验的完整阶段；若重建，在事务外收集并校验所有新候选，再在一个受租约保护的事务中替换旧集合。或者采用带完成标记的候选版本，失败版本不能清除已完成版本。不能把空集合、部分结果与完整无争议结果混为同一状态。

对应失败实例：`test_retry_failure_retains_previously_committed_dispute_stage`。
