## 2. 三个关键判断

### 2.1 「先检查后使用」在并发下不构成授权

第一轮我给清理函数加了 `_attempt_is_current` 的布尔检查，然后把 UPDATE 放进短事务。
**这是不够的**：查询在事务之外，两个动作之间另一个连接可以提交接管
（恢复扫描换 token，或新尝试开始），旧 worker 照样把当前资源改坏。

正确的形式是把**判定本身**放进写入所在的那个事务，并持 Job 行锁：

```python
with transaction.atomic():
    job = _locked_current_attempt(context, run)   # SELECT ... FOR UPDATE + 判定
    if job is None:
        return                                    # 接管已发生，整体跳过
    RunPaper.objects.filter(...).update(...)      # 同事务、同锁内写入
```

同一模式的另一个坑：单篇入口原先**先**把 status 改成 `processing`，**后**才由解析服务
校验租约。一个持旧 token 的 worker 因此会把**已经 ready** 的论文改回 processing，
随后才收到 `INVALID_JOB_STATE`——状态已经被改坏了。顺序必须反过来。

### 2.2 「事务块退出」不等于「已提交」

`with transaction.atomic()` 退出只代表"准备提交"，真正的 COMMIT 发生在块外。
我上一轮在块内就把 `committed_path` 置为 `None` 并注释"已提交"——提交阶段抛
`DatabaseError` 时，异常处理已经失去清理路径，于是留下无登记文件。

现在只有在 `with` 块**正常退出之后**才解除清理责任；清理前还会查一次
`FileAsset` 是否真的存在——**宁可留下一个可被后续清理的孤儿，也不能删掉已被引用的产物**。

### 2.3 空集合与"还没跑完"是两种状态

争议阶段的原策略是"进入时先删旧候选，随后逐主题追加"。第一个主题提交后第二个主题失败，
旧集合已被删除，于是"重试失败"反而把先前**完整提交**的成功产物弄丢。

改为：事务外把全部主题的候选算完并校验，然后用**一个**受租约保护的事务整体替换。
这样失败发生在任何数据库写入之前，旧集合原样保留；空集合也明确表示
"这次确实没有争议候选"，而不是"还没跑完"。

## 5. 仍未覆盖 / 已知限制

本轮的自动检查**不能**替代以下人工验收，也不改变这些已知简化：

1. **真实模型输出未冒烟**：全部检查使用替身。真实归纳质量、条件对齐合理性与
   引用合规率要等 M14。
2. **主题归纳仍是单批调用**：`04` 第 3 节要求"分批主题归纳、合并与成员映射"。
   当前把全部单篇要素放进一次调用；语料接近 30 篇时可能触及模型上下文上限。
3. **争议成员上限截断不告知用户**：超过 `max_papers_per_topic` 的成员被静默截断。
4. **`_save_topics` / `_save_disputes` 的替换策略会重建 ID**：同一 Run 内这些 ID 不稳定。
   争议的**逻辑调用 ID** 已改为稳定位置种子，不受影响。
5. **人工抽检**：主题划分与争议分类的学术合理性只能人工判断。
6. **恢复扫描与"新尝试开始"的并发窗口**由真实 PostgreSQL 行锁覆盖；
   SQLite 不能替代该结论。
