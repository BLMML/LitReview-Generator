## 2. 关键设计决定

### 2.1 本阶段不会出现 `Run.ready`

> **时点说明**：本条描述的是 **M07 完成当时**的行为。M09 落地后
> `index` / `topics` / `disputes` / `finalize` 四段已全部接通，
> 流水线现在能自己走到 `Run.ready`，`pending_stages` 机制**已移除**。
> 见 [M09 实现与验收](M09_实现与验收.md)。

M07 当时 `index`（M08）、`topics` / `disputes`（M09）、`finalize` 尚未实现。
因此全部论文抽取成功后，Run **显式失败**并在 `error.details.pending_stages`
点名上述阶段，Job 同步 `failed`。

这是刻意的：`04` 第 3 节要求完整 Run 的成功终态必须等所有必要阶段接通、在同一事务提交；
把不完整的 Run 标成 `ready`（或让 Job `succeeded`）会向下游谎报"分析可用"，
M10 的生成会基于缺失的主题 / 争议产出看似合理的正文。宁可让调用方看到明确的未实现错误。

### 2.2 幂等键必须落在真实 HTTP 路径上

`jobs.services.accept_job` 内部用它自己的 `/projects/{id}/jobs/{kind}` 约定路径构造幂等作用域。
若把 key 直接交给它，`POST /projects/{id}/runs` 的同键重放会**查不到记录**，
第二次请求被 `PROJECT_BUSY` 挡住（409），而不是按契约返回原 202。

因此 `create_run` 在 Project 行锁内先用**真实契约路径** `/api/v1/projects/{id}/runs`
调 `claim_or_replay`，再把返回的 `Claim` 传给 `accept_job`——既不重复记录受理响应，
也不重复投递，同时保证重放优先于忙状态。

### 2.3 冻结配置就是解析配置

`Run.config_snapshot["parsing"]` 直接存放 `parsing.config.effective_config()` 的结果，
worker 再把它原样传给 `parse_paper`。因此解析缓存身份（`config_hash`）与执行参数
来自**同一份快照**，不会出现"按新默认值解析、却按旧哈希缓存"的漂移。

若冻结的提示词版本与当前模板不一致，抽取阶段**显式失败**而不是用新模板生成后标旧配置。

### 2.4 逐篇失败不拖垮整批，但也不虚报

单篇失败记为 `RunPaper.failed` + 逐篇 `error`，继续处理其余论文；最终 Run `failed`，
`error.details.papers` 列出每一篇的失败原因，已提交的成功产物保留。
不使用"只汇总成功论文"的方式掩盖失败。

### 2.5 取消与租约失效分别收尾

`check_execution_lease` 只比对 token / 状态 / 取消意图，**不检查租约是否过期**。
恢复扫描尚未接管时 token 可能没变，这个窗口足以让旧 worker 写入结果。
`_locked_job` 因此显式补上 `lease_expires_at` 判断。

- 取消：RunPaper 交回 `pending`、Run `cancelled`、停止后续模型调用；
- 租约过期 / 被取代：交回 `pending` 后**向上抛出**，由 `jobs.tasks` 统一收尾
  （过期 → 恢复扫描判 `WORKER_LOST`），Run 保持 `processing` 不做终态判定。

## 3. 本轮修正的 3 个既有缺陷

这三个都不是 M07 引入的，而是在接通链路时暴露出来的：

### 3.1 `common/http.py` 兜底分支会抛 TypeError（严重）

```python
api_error(code, str(exc.detail), status_code=exc.status_code)   # api_error 没有该参数
```

`api_error()` 辅助函数不接受 `status_code`，需要自定义状态码时必须直接构造 `ApiError`。
后果：**任何**不是 ApiError / Http404 / PermissionDenied / ValidationError / Throttled 的
DRF 异常（405、415、406、401 的其它形态…）都会在**异常处理器内部**再抛一次 `TypeError`，
客户端拿到 500，且没有任何可读原因——完全绕过契约要求的错误 envelope。

修复：直接构造 `ApiError(code, message, status_code=...)`。
新增 `tests/test_error_envelope.py`（8 条）逐一覆盖 405/415/404/400/406/401。

### 3.2 `GET /runs/{id}/retrievals` 从未挂载视图

`retrieval/api.py` 的 `urlpatterns` 只注册了 POST 的 `run_retrievals_create`，
而**同名的 list 视图 `run_retrievals_list` 没有任何路由指向它**。于是：
`GET` 落到 405 兜底分支 → 叠加 3.1 的 TypeError → 500。

契约要求该路径同时支持 GET（"用于恢复历史查询"）与 POST。已合并为一个端点函数，
并为 list 补上 Run 归属校验：他人的 Run 返回 404，而不是"200 + 空列表"。

### 3.3 证据列表接口直接返回模型实例

`paper_evidence_list` 把 `EvidenceChunk` queryset 交给 DRF 渲染 →
`TypeError: Object of type EvidenceChunk is not JSON serializable`（500）。
新增 `list_evidence_dtos()` 返回契约规定的 `EvidenceDTO` 字典，并给原 queryset 函数
补上"返回的是模型实例、HTTP 层必须自行序列化"的警示注释。
