## 2. 关键设计决定

### 2.1 索引产物是 JSON，不是 pickle

`04` 第 3 节要求 index 阶段产出"Run 专属索引文件与 manifest"，`02` 把
`AnalysisRun.index_asset` 定义为"完整索引发布后一次性填写"。M08 用的是纯内存索引，
`index_asset` 永远是 null——这是 M08 留下的契约缺口，M09 补上。

补的方式是**纯 JSON 产物**：只保存词表、IDF 与每片的稀疏权重，加载后由本进程重建。
理由与 M08 一致——契约禁止接收用户上传的 pickle / joblib，那就不引入反序列化执行
代码的面。JSON 还带来一个 M08 没有的好处：**加载时能逐字段校验**（格式版本、
列索引范围、权重有限性、manifest 与当前源是否一致）。

为此 `index.py` 不再依赖 scikit-learn：TF-IDF 与余弦都在本项目内实现。这样索引的
**每一个数值**都能完整写进产物并读回校验，不存在"矩阵与向量器两套状态"的漂移。

### 2.2 索引复用按**源摘要**校验，不只看"文件在不在"

`manifest` 里带 `source_digest`：全部证据片段的 ID、页号、顺序与文本的 SHA256。
加载产物时先比对 `run_id` / `analysis_revision` / `source_digest`，任一不符就
**记 warning 后内存重建**——绝不拿对不上的索引去排序。

解析产物被重建（例如解析器版本升级后重新解析）而索引还是旧的，会给出指向已不存在
内容的排序，这是比"索引缺失"更危险的状态：缺失会重建，不一致如果不检查就会静默使用。

### 2.3 争议只在**同一主题内**比较，且白名单随之收窄

`04` 第 3 节把 disputes 的输入定为"同主题论文候选"。实现上每个主题一次调用，
`allowed_paper_ids` 收窄到**该主题成员**，`allowed_evidence_ids` 收窄到这些成员的片段。

这比"传全 Run 的论文然后过滤输出"更强：模型在提示词里根本看不到主题外的候选，
跨主题引用在网关白名单这一层就被拒。单篇主题不发起调用——没有可比较的对象，
发一次必然只能返回空数组的调用是浪费。

### 2.4 单篇主题与零争议都是合法结果

"没有争议候选或某主题只有少数文献是合法结果，不要求模型凑数"（`04` 第 3 节）。
因此：
- 单篇主题直接跳过，不调用模型；
- 模型返回 `disputes: []` 正常落库为零条；
- 争议阶段不因"没找到冲突"而失败。

### 2.5 人工复核字段与自动分类严格分离

`Dispute` 的 `classification` / `reason` / `claims` 是自动产物，
`review_status` / `review_note` / `version` 是人工字段。`DisputePatchSerializer` 是
`StrictSerializer`，因此"顺手把 classification 一起改了"的请求会被 400 挡在门外，
而不是被静默忽略——测试专门验证了这一点。

### 2.6 Run 级阶段失败也要收尾

逐篇失败的收尾在 M07 已实现。M09 补上 Run 级阶段（index / topics / disputes）的收尾：
`_finish_stage_failed` 把 Run 置为 failed 并写错误，**已完成的逐篇产物与索引产物保留**，
因此重试可以只补 Run 级阶段。

## 3. 本轮修正的 1 个既有缺陷

### `_frozen_config` 抛错时 Run 永远停在 `processing`

`_frozen_config` 原先在任何 `try` 之外调用。它抛出的 `ApiError` 会直接冒到
`jobs.tasks.execute_job`，被统一收敛成 `Job.error` —— 但 **Run 没有任何人收尾**，
永远停在 `processing`。前端看到的是一个既没完成、也没原因的 Run，只能人工查库。

这个缺陷在真实使用中才会暴露：M09 给 `config_snapshot` 加了 `topics` / `disputes`
两段，于是**所有 M09 之前创建的 Run 都会命中**。修复是把调用包进 `try`，
走 `_finish_stage_failed` 正常收尾；旧 Run 现在会明确告知"缺少冻结配置快照，请新建分析"。

回归由 `test_missing_frozen_config_fails_run_instead_of_hanging` 守住，
并已用回退修复验证过它确实会失败。

## 6. 仍未完成 / 需要人工确认

1. **真实模型输出未冒烟**：本轮全部用替身。真实 `assign_topics` / `compare_disputes`
   的归纳质量、条件对齐合理性与引用合规率要等 M14。
2. **主题归纳是单批调用**：`04` 写的是"分批主题归纳、合并与成员映射"。当前实现把全部
   单篇要素放进**一次**调用（受 `TOPICS_MAX` 与模型输入上限约束）。语料接近 30 篇时
   输入可能触及模型上下文上限——届时需要真正的分批与合并。**这是已知的实现简化，
   不是已完成的分批逻辑。**
3. **争议比较是 O(主题成员数²)**：每个主题一次调用，成员上限由
   `DISPUTES_MAX_PAPERS_PER_TOPIC`（8）限制。超过上限的成员被截断，
   截断行为本身没有告知用户。
4. **索引为每个 Run 各存一份**：语料 30 篇时体积可接受，但同一批文献在多个 Run 之间
   不共享索引。语料显著变大时需要重新评估。
5. **人工抽检**：主题划分与争议分类的**学术合理性**只能人工判断；
   自动测试只能证明结构、归属与顺序正确。
