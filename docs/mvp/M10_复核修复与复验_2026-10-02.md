## 1. 修复对应关系

| 原问题 | 修复后的行为 |
| --- | --- |
| 项目忙碌时仍能保存正文 | 锁 Project 后检查活跃 Job；queued / running / cancelling 时保存返回 409 PROJECT_BUSY，不增加正文版本 |
| 受理时冻结旧分析版本 | Project 锁内重新锁定和读取 Run，再做可生成检查、冻结 analysis_revision 和创建 Review / Job |
| 正式 Job 重试撞上已登记的网络尝试 1 | 读取同一逻辑调用的历史账本，从下一次尝试继续；保留稳定身份、成功缓存、三次上限及最多一次格式修复 |
| target_chars 没有参与生成 | 冻结总目标和分节目标，以 15% / 25% / 30% / 15% / 15% 分配五节篇幅，并传入提示词；证据不足允许缩短，不强制精确字数 |
| 内部检索读取新部署配置 | 受理时冻结扩展 / 重排模板和模型参数、实际候选与 top_k 限制、查询和章节要求；执行显式透传 |
| 内部重排使用随机逻辑 ID | 从 Review ID 与章节派生稳定检索身份，扩展与重排均使用该身份；重试不更换 ID 绕过次数限制 |
| 单节 block 上限只约束提示词 | 网关、单节结构检查和全稿发布前检查均执行冻结上限；超限输出不进入成功缓存，也不发布正文 |
| 某节无证据导致整份正文 PDF_PARSE_FAILED | 后端生成一个说明覆盖限制的合法 transition，使用后端 block UUID、空 evidence_ids；继续完成五节校验后一次性提交 |

另补齐生成请求的幂等兼容：新请求的指纹保留客户端字段是否缺失，不依赖新部署默认值；旧 `review-gen-v1` 记录按原 Review 的参数核对旧指纹，重放原受理结果，不改写历史。同键异体仍返回 IDEMPOTENCY_CONFLICT。

正文发布也按 `02` 的统一锁序取得 Project → Review → Job，并在锁内计算新版本号。
补充真实连接间的取消竞争检查确认：取消先取得项目写锁时，发布等待取消提交后拒绝创建正文。
取消接口的鉴权 JOIN 改为只锁 Job，避免连带锁 Project 干扰发布中的取消。
本轮复现了该 JOIN 导致的等待超时，没有复现数据库死锁，未把推测的死锁记为已确认缺陷。

## 4. 在当前电脑使用修复版本

1. 重启 Django Web 与 Celery worker，使长驻进程重新加载代码及提示词。
2. 原生成配置升级为 `review-gen-v2`。旧 v1 未完成 Review 缺少完整冻结参数，不能用当前配置补成历史快照；需要使用新 Idempotency-Key 重新创建综述。当前本地开发数据库只读检查发现 **2 份**这样的旧综述，没有删除或改写它们。
3. 已有正文 / 历史版本可继续读取；项目空闲时可以正常编辑保存。旧幂等键重放仍返回原 Job，不会自动受理新的 v2 任务。
4. 新综述可用默认 3000 字目标，或选择 2000—4000 字；查看五节正文、证据不足说明，编辑后确认保存为新版本。
5. 后续开发 M11：指定正文版本核验、结构 / 语义报告、警示确认及 Word 导出。

Web 终端：

```powershell

```

