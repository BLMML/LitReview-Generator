## 2. 已复现的问题

### 1. [P1] 项目忙碌时仍能保存正文（3 条失败）

位置：[reviews/services.py:449](<D:/LitReview Generator/backend/apps/reviews/services.py:449>)。

触发：已有 revision 1，项目新受理一个检索任务，任务分别处于 `queued`、`running`、`cancelling` 时，向 `/reviews/{id}/revisions` 提交合法正文及 `base_revision_number=1`。

实际：三种状态均返回 **201** 并创建 revision 2；应返回 **409 PROJECT_BUSY**，版本数量不变。`save_revision` 只锁 Project 与 Review，没有调用 `require_project_idle`。这违反 [00:97](<D:/LitReview Generator/docs/mvp/00_开发基线与范围.md:97>) 的项目写入串行约束，并允许后台生成/核验/导出与正文修改同时发生。

修复：取得 Project 行锁后、修改 Review 前检查项目忙碌状态；保留旧 Run 草稿在项目空闲时的编辑能力。

### 2. [P1] 综述受理冻结锁前读取的旧分析版本（1 条失败）

位置：[reviews/services.py:133](<D:/LitReview Generator/backend/apps/reviews/services.py:133>)、[reviews/services.py:157](<D:/LitReview Generator/backend/apps/reviews/services.py:157>)。

触发：创建综述请求先读取 `Run.analysis_revision=1`，尚未取得 Project 锁；另一数据库连接通过正常 `review_dispute` 服务确认争议，成功将 Run 推进到 revision 2；随后综述请求取得锁并完成受理。

实际：受理返回 202，但 Review 及 Job 的冻结输入仍记录 **analysis_revision=1**。生成阶段会读取现在的争议数据，导致输入实际版本与正文记录的冻结版本不一致，新正文也可能立即显示过时。

原因：`create_review` 在事务外读取 Run；取得 Project 锁后仍使用旧对象。

修复：遵守 Project → Run/资源 → Job 的锁顺序；取得 Project 锁后重新读取或锁定 Run，并在同一受理事务内完成可生成检查与版本冻结。依据：[03:121](<D:/LitReview Generator/docs/mvp/03_HTTP接口契约.md:121>)。

### 3. [P1] 已知零用量限流后的正式重试立即失败（1 条失败）

位置：[llm/client.py:338](<D:/LitReview Generator/backend/apps/llm/client.py:338>)、[llm/budget.py:95](<D:/LitReview Generator/backend/apps/llm/budget.py:95>)；生成章节使用稳定 ID 的位置为 [reviews/services.py:327](<D:/LitReview Generator/backend/apps/reviews/services.py:327>)。

触发：前四节经真实网关生成成功；第五节第一次供应商响应是可重试限流、已知零用量，且 Retry-After 超出单次等待上限。第一次 Job 正常失败，错误为 `MODEL_RATE_LIMITED`，`retryable=true`，第五节账本只有网络尝试 1。随后调用正式 `retry_job`，执行新 Job。

实际：新 Job 再次失败，错误为 **INVALID_JOB_STATE：该逻辑调用的网络尝试已受理**，没有正文。网关每次入口都从网络尝试 1 开始；第五节稳定逻辑 ID 的尝试 1 已存在，而允许的尝试 2、3 尚未使用。

这是 M10 重试链暴露的模型调用底座问题。修复应恢复账本中的合法下一次尝试，并协调并发认领、成功缓存和重试总次数；不能通过随机更换逻辑 ID 绕过“单逻辑调用最多 3 次”的约束。未决费用也不能直接视为已结算。依据：[03:161](<D:/LitReview Generator/docs/mvp/03_HTTP接口契约.md:161>)、[04:148](<D:/LitReview Generator/docs/mvp/04_后台流程与DeepSeek规范.md:148>)。

### 4. [P2] `target_chars` 没有参与生成（1 条失败）

位置：[reviews/services.py:305](<D:/LitReview Generator/backend/apps/reviews/services.py:305>)。

触发：同一 Run 分别受理目标 2000 字与 4000 字的综述，捕获五节生成请求。

实际：两份综述的五节生成参数完全相同；`target_chars` 只保存在 Review 上，既未进入章节指令，也未影响篇幅分配或模型输出预算。实现记录第 6 节也已承认这一缺口。

修复：把目标总篇幅和合理的分节篇幅目标传入生成指令并冻结相关参数。这里要求目标影响生成；[00:16](<D:/LitReview Generator/docs/mvp/00_开发基线与范围.md:16>) 明确长度是生成目标，**不是精确字数的绝对保证**，不能据此要求每次输出必须严格达到某个字数。

### 5. [P2] 内部检索的模型配置未随 Review 冻结（1 条失败）

位置：[reviews/services.py:551](<D:/LitReview Generator/backend/apps/reviews/services.py:551>)、[retrieval/services.py:332](<D:/LitReview Generator/backend/apps/retrieval/services.py:332>)。

触发：先受理 Review，再改变部署模型输出上限，随后执行生成并捕获内部查询扩展/重排请求。

实际：正文生成使用冻结配置，但内部检索请求读取修改后的模型配置。`_section_evidence` 调用 `retrieve_evidence` 时没有传 `config`，该入口回退到当前 `_build_config_snapshot()`。现有 `analysis_config` 不能替代本次内部扩展与重排配置。

修复：受理时冻结生成依赖的检索模板版本、模型参数与实际检索限制，并显式传给内部检索入口。保留既有 Run 冻结索引配置的透传。依据：[02:171](<D:/LitReview Generator/docs/mvp/02_数据模型与一致性.md:171>)、[04:89](<D:/LitReview Generator/docs/mvp/04_后台流程与DeepSeek规范.md:89>)。

### 6. [P2] 同一综述同一章节的内部重排使用随机逻辑 ID（1 条失败）

位置：[retrieval/services.py:632](<D:/LitReview Generator/backend/apps/retrieval/services.py:632>)；调用方：[reviews/services.py:551](<D:/LitReview Generator/backend/apps/reviews/services.py:551>)。

触发：对同一受理 Review 的同一章节重复执行内部选证据，捕获重排请求的 `logical_call_id`。

实际：两次 ID 不同。M10 没有提供内部检索标识；默认配置也没有 `run_id`，`_retrieval_seed` 最终回退到随机 UUID。失败或尚无成功缓存的重排在 Job 重试时无法保持同一逻辑调用身份，可能绕过累计尝试次数约束。

修复：从稳定的 Review ID 与章节/内部阶段身份派生调用标识，并与冻结的内部检索配置一起传入。现有成功缓存仍可能命中，本项**不表示每次成功重排重放都会再次付费**。

### 7. [P2] 单节 block 上限只写入提示词，后端不执行（1 条失败）

位置：[reviews/services.py:366](<D:/LitReview Generator/backend/apps/reviews/services.py:366>)。

触发：受理时 `REVIEW_MAX_BLOCKS_PER_SECTION=1`，确认快照保存上限 1；模型每节返回 2 个合法 block，全稿仍小于 100 个 block。

实际：正常提交成功，每节包含 2 个 block。`_validated_section` 校验了通用 Schema，但没有检查冻结的单节上限。默认上限 20 同样只有提示词约束。

修复：生成结果校验显式应用冻结单节上限，超限拒绝发布；保留五节整体结构和总 block 数检查。依据：[04:92](<D:/LitReview Generator/docs/mvp/04_后台流程与DeepSeek规范.md:92>)。

### 8. [P2] 单节无证据时整个综述失败，未输出覆盖限制（1 条失败）

位置：[reviews/services.py:295](<D:/LitReview Generator/backend/apps/reviews/services.py:295>)。

触发：其他章节证据正常，`disagreements` 章节没有相关证据。

实际：抛出不可重试的 **PDF_PARSE_FAILED：本节没有可用证据，无法生成正文**，不提交任何正文。没有检索到该节相关证据，并不等同于 PDF 解析失败。

冻结规范 [04:81](<D:/LitReview Generator/docs/mvp/04_后台流程与DeepSeek规范.md:81>) 要求证据不足章节输出明确覆盖限制，可使用无引用 transition 说明“本轮证据不足以形成判断”。修复应生成合法的覆盖限制章节，继续进行完整五节校验；空模型响应、坏引用仍须拒绝，不能编造 claim 填补证据缺口。

## 3. 建议修复及验收顺序

1. 修复正文保存的 PROJECT_BUSY 检查与受理时版本冻结竞争。

3. 冻结并传入内部检索配置，为内部重排提供稳定的调用身份。
4. 实现目标篇幅指令、冻结单节 block 上限校验及证据不足章节的覆盖说明。
5. 重跑本轮独立检查；全部通过后再跑项目全量测试，更新 M10 验收记录。独立检查与全量测试共享测试数据库时，不要并行执行。
