# 本机启动流程

**适用版本**：`v0.12.0-m12-raw-workbench`（M12 前端工作台已交付）
**验证日期**：2026-10-03
**适用平台**：Windows + PowerShell（仓库本身在 `D:\LitReview Generator`）

本文只讲「怎么把服务跑起来」。业务操作步骤见 [M12 实现与验收](mvp/M12_实现与验收.md)，
目录职责见 [01 文件架构与职责](mvp/01_文件架构与职责.md)。

---

## 一、要启动的五个组件

| 组件 | 监听地址 | 作用 | 必需性 |
| --- | --- | --- | --- |
| PostgreSQL | `127.0.0.1:5432` | 数据库；行锁、并发受理、部分唯一索引都靠它 | 必需（M13 前不回退） |
| Redis | `127.0.0.1:6379` | Celery 队列与临时协调，不做持久化 | 必需（否则任务不执行） |
| Django | `127.0.0.1:8000` | 后端 HTTP API | 必需 |
| Celery worker + beat | 无端口 | worker 跑分析 / 检索 / 生成；beat 跑定时对账与清理 | 必需（否则任务停在 queued） |
| Vite 前端 | `127.0.0.1:5173` | 工作台界面，`/api` 反代到 8000 | 必需（入口） |

**浏览器入口是 http://127.0.0.1:5173**，不是 8000。8000 只提供 API，直接打开只会看到 JSON。

> 任务真实状态永远在数据库里。投递失败的任务会保持 `queued`，由 beat 的 `reconcile_jobs` 补发，
> 不以队列 ACK 推导成功。所以 **beat 不是可选项**。

## 二、首次准备（只做一次）

### 1. Python 依赖

前置 Python **3.12**（基线冻结）。仓库根已有 `.venv`：

```powershell
cd 'D:\LitReview Generator'
.venv\Scripts\python.exe -V                       # 应为 3.12.x
.venv\Scripts\python.exe -m pip install -r requirements.lock
```

### 2. `.env`

```powershell
Copy-Item .env.example .env        # 已存在则跳过，不要覆盖已有配置
```

本机 `.env` 当前的关键值（本次核对）：

| 变量 | 当前值 | 说明 |
| --- | --- | --- |
| `APP_ENV` | `development` | 数据库缺失时会回退 SQLite 并告警 |
| `DJANGO_DEBUG` | `true` | 开发用；走查 / 端到端时要临时改 `false` |
| `DATABASE_URL` | `postgresql://review:…@127.0.0.1:5432/review_mvp` | 由 PG 初始化脚本自动写入 |
| `REDIS_URL` | `redis://127.0.0.1:6379/0` | 与本地 Redis 一致 |
| `LLM_MODE` | `real`（本机已授权） | 默认安装为 mock；本机真实任务按项目预算调用 DeepSeek |
| `LLM_MAX_INPUT_TOKENS` | `384000` | 支持约三万字单篇 / 双篇比较 |
| `DEEPSEEK_API_KEY` | 本机已配置，不展示 | 前端不读取密钥，密钥只在后端 |

`.env` 不入库；不要在文档或聊天里贴出 `DJANGO_SECRET_KEY` 与数据库密码。

### 3. PostgreSQL 与 Redis 的免安装二进制（本机走这条路线）

本机不用系统服务，而是用 `.data/` 下的免安装副本 + 自带控制脚本：

```powershell
cd 'D:\LitReview Generator'

# 下载并解压 PostgreSQL 免安装包（约 300 MB，解压到 .data/pgsql）
.venv\Scripts\python.exe .data\tools\setup_pg.py

# 下载 Redis for Windows 到 .data/redis
.venv\Scripts\python.exe .data\tools\setup_redis.py

# 初始化 PG 集群 + 建库建用户 + 把 DATABASE_URL 写入 .env + 自动启动
.venv\Scripts\python.exe .data\tools\pg_ctl_local.py init
```

`init` 会自动挑选 ASCII 安装路径（优先 `D:\review-mvp-pg`，其次 `%PUBLIC%\review-mvp-pg`）。
**这是硬约束**：PostgreSQL 在含中文的路径下 initdb 必然失败，不要搬到中文目录。

### 4. 数据库迁移与账号

```powershell
cd 'D:\LitReview Generator\backend'
..\.venv\Scripts\python.exe manage.py migrate
..\.venv\Scripts\python.exe manage.py createsuperuser   # MVP 没有注册接口，账号只能这样建
```

已有账号见 `docs/登录账号.xlsx`。测试账号不要用于正式部署。

## 三、日常启动（四个终端）

按 ①②③④ 顺序执行；②③④ 可并行，但都要求 ① 已完成。

### ① 数据库与 Redis

```powershell
cd 'D:\LitReview Generator'
.venv\Scripts\python.exe .data\tools\pg_ctl_local.py start
.venv\Scripts\python.exe .data\tools\redis_local.py   start
```

PG 首次启动会做崩溃恢复与 fsync，可能等几十秒；脚本用 `-w -t 120` 等待，属正常。

### ② Django 后端

```powershell
cd 'D:\LitReview Generator\backend'
Remove-Item Env:LLM_MODE -ErrorAction SilentlyContinue
..\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

### ③ Celery worker 与 beat（两个终端）

```powershell
cd 'D:\LitReview Generator\backend'
Remove-Item Env:LLM_MODE -ErrorAction SilentlyContinue
..\.venv\Scripts\python.exe -m celery -A config worker --pool=solo --loglevel=INFO
```

```powershell
cd 'D:\LitReview Generator\backend'
Remove-Item Env:LLM_MODE -ErrorAction SilentlyContinue
..\.venv\Scripts\python.exe -m celery -A config beat --loglevel=INFO
```

Windows 上 worker **必须** `--pool=solo`，默认 prefork 池在 Windows 上不可用。

### ④ 前端

```powershell
cd 'D:\LitReview Generator\frontend'
npm.cmd run dev
```

首次或依赖变更后先 `npm.cmd ci`（`node_modules` 已存在时可跳过）。
Vite 端口固定 5173 且 `strictPort: true`：端口被占用会直接报错退出，而不是换端口。

然后打开 **http://127.0.0.1:5173** 登录。

## 四、启动核对（30 秒）

```powershell
cd 'D:\LitReview Generator'
.venv\Scripts\python.exe .data\tools\pg_ctl_local.py status   # 期望「状态：运行中」
.venv\Scripts\python.exe .data\tools\redis_local.py   status  # 期望「状态：运行中」
```

```powershell
# 四个端口都应在监听
foreach ($p in 5432,6379,5173,8000) {
  $c = Get-NetTCPConnection -LocalPort $p -State Listen -ErrorAction SilentlyContinue
  "$p : " + $(if ($c) { "监听中" } else { "未监听" })
}
```

```powershell
# 后端确实在跑（未登录应返回 401/403，而不是连接失败）
try { Invoke-WebRequest http://127.0.0.1:8000/api/v1/me -TimeoutSec 5 | Out-Null } catch { $_.Exception.Response.StatusCode.value__ }
```

worker 是否真的连上 Redis，看 ③ 的终端是否出现 `celery@… ready`；前端是否连上后端，登录页能登录即说明代理通。

## 五、停止与重启

```powershell
cd 'D:\LitReview Generator'
.venv\Scripts\python.exe .data\tools\redis_local.py   stop   # 走 redis-cli shutdown，干净退出
.venv\Scripts\python.exe .data\tools\pg_ctl_local.py stop    # pg_ctl stop -m fast
```

②③④ 是前台进程，在各自终端按 **Ctrl+C**。Django 用普通 `runserver`（没有 `--noreload`）时改代码会自动重载，不需要重启。

**改了 `.env` 必须重启 Django 与 worker**，配置不会自动生效；历史失败任务也不会因为改配置而变好，需要重新发起分析。

## 六、常见故障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `manage.py` 报连不上数据库 | PG 没启动 | 先跑 ① 的 `pg_ctl_local.py start` |
| 上游测试批量报连接错误 | 同上；`.env` 里有 `DATABASE_URL`，PG 未启动时测试直接失败 | 启动 PG 后再跑测试 |
| 任务一直 `queued` | worker 或 beat 没起 / Redis 没起 | 检查 ③ 与 `redis_local.py status` |
| 页面 5173 打不开但 8000 正常 | 前端没启动，或 5173 被占用 | 看 ④ 终端报告；释放端口 |
| 登录成功但接口 401 | `DJANGO_SECURE_COOKIES` 被设成 `true` 而当前是 HTTP | 未接 TLS 前保持 `false` |
| 走查 / 端到端脚本行为异常 | `DJANGO_DEBUG` 仍为 `true` | 临时设 `$env:DJANGO_DEBUG='false'`，重启 Django |
| venv 里的 `ruff.exe` / `pytest.exe` / `celery.exe` 报路径错误 | 这些包装脚本嵌了创建时的绝对路径 | 一律改用 `.venv\Scripts\python.exe -m <模块>` |
| PG 初始化报 `invalid byte sequence for encoding "UTF8"` | 安装路径含中文（PG 的已知 bug，官方不修） | 用 `pg_ctl_local.py init` 让脚本挑 ASCII 路径 |
| `.data` 下的脚本写日志报「访问被拒」 | 目录 Windows 权限异常 | 见第八节 |

## 八、已知环境问题：`.data` 目录权限

2026-10-02 曾出现工作区根目录缺少「取得所有权」权限，导致沙箱无法授权写入；修复后，
2026-10-03 又发现 `.data` 目录出现同类写入受限问题——表现是
`pg_ctl_local.py status` 报 `PermissionError: … .data\pg_ctl_local.log`，
即脚本连自己的日志都写不了，**这会直接挡住第 ① 步**。

处理方式与上次相同：用仓库外的诊断脚本检查并修复该目录的 Windows 权限
（只为当前登录用户补上完全控制，改动前备份，可用生成的恢复脚本回滚）。
提权前不要用其它方式手工改权限，也不要把服务搬到别的路径绕开。

```powershell
cd 'D:\LitReview Generator'
python deploy\verify_stack.py        # 一键验证：渲染、构建、健康、迁移、worker、beat、容器内全量测试
```

手动分步：

```powershell
docker compose up -d --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser

docker compose logs -f worker
```

与本地路线的三点不同：

1. 入口是 **http://127.0.0.1:8000**——前端 nginx 独占回环 8000，Django 只在容器网络内 `expose`；
2. 数据库与 Redis **不发布到宿主机**，容器内 `APP_ENV=production`、`DJANGO_DEBUG=false` 强制注入，不跟随本地 `.env`；
3. worker 不需要 `--pool=solo`（容器内是 Linux）。

本机没有 Docker，[deploy/frontend.Dockerfile](../deploy/frontend.Dockerfile) 与
[deploy/nginx.conf](../deploy/nginx.conf) **没有做过真实构建验证**，TLS、真实容器、备份恢复都留在 M13。
`.data/tools/validate_deploy.py` 的 56 项结论基于旧的后端骨架和旧端口假设，**不能**当当前配置的验收证据。

## 十、边界：启动阶段不要做的事

- **不要执行真实付费模型调用**。默认 `LLM_MODE=mock`；切 `real` 只在 M14 期间、且是负责人明确要求时。
- 不要把 `.env`、密钥、真实用户数据写进文档或提交入库。
- 不要用「允许任意来源 + 携带凭据」解决跨域；同域靠 Vite / nginx 的 `/api` 代理。
- 不要把 PostgreSQL 或项目搬到含中文的路径。
- 启动日志建议按 `.data/service-logs/<时间戳>/` 归档，便于事后定位（该目录不进版本库）。
